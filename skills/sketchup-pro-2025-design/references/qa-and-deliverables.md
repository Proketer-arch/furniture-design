# Проверка, диагностика и выдача

## 1. Контрольные этапы

| Этап | Проверить | Доказательство |
|---|---|---|
| Вход | Файл/версия, единицы, обмер, активный контекст, сохраняемые объекты | Статус, контрольные размеры, источники |
| Основа | Геометрия оболочки/корпуса, толщины, проемы | Численные размеры, план/сечение |
| Наполнение | Детали, полезные объемы, техника и механизмы | Структура, ведомость, схемы |
| Функция | Открывание, проходы, монтаж, обслуживание | Рабочие положения и расстояния |
| Оформление | Теги, сцены, материалы, размеры | Восстановление сцен и характерные виды |
| Экспорт | SKP/LayOut/PDF/PNG, редакции и зависимости | Чтение файла и просмотр каждого листа |

При простой локальной правке проверяй затронутый объект и зависимости; полный цикл не обязателен. При изменении толщины/масштаба/механизма пересчитай зависимые детали и листы.

## 2. Сбои: наблюдение → гипотеза → проверка

| Симптом | Что различить до исправления |
|---|---|
| Объект исчез | Сцена, тег, hidden state, родитель, section plane, камера или реальное удаление |
| Размер отличается | Единицы импорта, отображаемая точность, локальные/мировые оси, масштаб, wrong context |
| Изменилась вся серия деталей | Общая definition, вложенная общая definition, случайное изменение типа вместо экземпляра |
| Грани слипаются | Сырая geometry в одном контексте, отсутствующая группа/компонент |
| Boolean не работает | Незамкнутый объем, внутренняя geometry, малые ребра, неподходящий объект, недоступная функция |
| Текстура неверна | Назначение грани/группы, нормаль, UV, масштаб и источник |
| PDF обрезан | Сцена, камера, viewport, масштаб, capture area, исходные разнесенные объекты |
| Мост не отвечает | Приложение, runtime tools, версия расширения, очередь, ожидание UI, фактический результат |

Не делай erase/purge/reset/restart до локализации причины. Сначала прочитай нужные данные и поставь обратимую проверку. Не считай Undo универсальным откатом внешних файлов.

## 3. Шаблон задания

- Проект, модель/путь, редакция, дата.
- Режим: интерьер/мебель/правка/документация/параметризация.
- Нужный результат и критерии приемки.
- Единицы, координаты, размеры и источники.
- Целевые объекты/ID и сохраняемые объекты.
- Материалы/толщины/механизмы: подтвержденное и условное.
- Требования к видам, сценам, листам и экспорту.
- Ограничения обмера, производства, монтажа и среды.
- Открытые вопросы с влиянием на результат.

Если информации хватает, не заставляй пользователя заполнять все поля: извлеки данные и начни работу. При нехватке критического значения спроси только его, продолжая независимую часть.

## 4. Паспорт модели и структура выдачи

```text
project_id / revision / date / stage
source_model / output_model
units / coordinates / origin / axes
measurement_sources / assumptions
object_ids / part_ids / material_status
scenes: name / purpose / camera / section / visible sets
outputs: path / format / scene / scale / revision
checks: method / expected / actual / result
open_items: issue / impact / action / owner
```

Для технической мебели дополнительно: части, чистовые размеры, раскройные параметры при подтверждении, кромки, текстура, обработка и ссылки на фурнитуру. Для интерьера: чистовые привязки, планы и задания профильным специалистам.

Файлы называй с проектом, редакцией и назначением. Проверяй, что `.layout` связан с нужным SKP, а не старой копией. Не переименовывай существующие пользовательские файлы без причины и учета ссылок.

## 5. Выходной отчет

Начинай с созданного результата. Затем перечисли существенные изменения, артефакты, фактические проверки и оставшиеся ограничения. Не своди доказательство к «команда выполнена».

Статусы различай:

- Концепция: размеры/материалы могут быть условными.
- Геометрия проверена: размеры и структура подтверждены.
- Документация подготовлена: файлы выпущены и просмотрены в указанном объеме.
- Конструкция проверена: есть требуемые расчеты/документы.
- Технология согласована: имеется реальная проверка производства.
- Изделие испытано: имеется протокол фактического образца.

Готовность одной стадии не устанавливает другие. На вопрос «можно ли производить?» перечисляй оставшиеся конкретные данные и проверки.

## 6. Сценарии проверки навыка/алгоритмов

Для анализа инструкций или изолированной разрешенной проверки используй:

1. Комната с чистовым размером 4000×3000: batch room должен учитывать наружные размеры и t, а не создавать меньший внутренний объем молча.
2. Деталь с поворотом: локальные L/B/t не заменяются мировым axis-aligned bounding box.
3. Два экземпляра компонента: изменение одной позиции не меняет другой без проектного основания.
4. Несохраненный пользовательский файл: смена модели/перезапуск не уничтожает его.
5. Таймаут записи: сначала чтение объектов/выходов, без дублирования.
6. План в LayOut: сохраняется правильная сцена/разрез и scale=50 означает 1:50.
7. Разнесенные объекты: успешный экспорт не объявляется доказательством полноты PDF.
8. Материал 2025: наличие RGB в batch не объявляется созданием PBR-материала.
9. Нет LayOut tool в runtime: исходник сервера не подменяет реально доступный инструмент.
10. Импорт техники: размеры установки подтверждаются документом, а не библиотечной моделью.

Тест инструкции, вызов schema validator, проверка API на копии и реальная модель — разные уровни. В отчете назови выполненный уровень.

## 8. Приёмка мебельной сборки

Для всех участников сборки, в том числе объектов вне сметы и созданных отдельным Ruby-скриптом, сохранить роли/ID, родителя, локальные размеры, мировое преобразование, базу привязки и редакцию. Различать корпус, монтажный габарит от стены и видимые поверхности. Подтверждённый внешний технический зазор не переопределять типовой столешницей.

Для стыка задать обе поверхности, границы, вид соединения/шва, размер и допуск. Сравнивать геометрию в общей системе: совпадение X-краёв фартука и пенала не исключает разрыв по Y. Проверять именно внутреннюю боковину у фартука, а не только внешнюю облицовку. Проверять маршрут цоколя против боковин до пола, опор/клипс, вентиляции и хода двери ПММ. Отступ цоколя, его толщина и ось опоры — разные величины. Результат пересечения BoundingBox уточнять реальным контуром/сечением/объёмом.

Обязательные доказательства: общие цепи/фронт, план столешницы/фартука, цокольное сечение с опорами и боковинами, внутренние примыкания к пеналам, сложные углы и рабочие положения подвижных частей. Выбирать виды под измеряемый узел. Для дизайна без чертежей это рабочий контроль, не поручение выпускать альбом.

После изменения ширины/боковин/глубины/механизма отменить прежнюю приёмку зависимых узлов и проверить новую редакцию. До обновления параметрического компонента сравнить паспорт с фактической геометрией вложенных деталей. Сохранить ручные правки и согласовать параметры либо явно ограничить регенерацию; не терять их молча.

Ожидаемые размеры/примыкания получать из задания независимо от экспортёра. Проверка замкнутости и объёма подтверждает детали, сравнение с собственным экспортом — сохранение. Раздельно сообщать результаты модулей, сборки, кинематики, ведомости/стоимости, сохранения и производства. Запись: `редакция | ID узла | требование/источник | метод | ожидаемое | фактическое | результат | вид/файл`. При дефекте либо непроверенном обязательном узле общего положительного итога нет.

При задании испытать расширение использовать его интерфейс/поддерживаемый API для проверяемого построения и пересчёта. В отчёте указать, что создано расширением, отдельным скриптом или вручную; самостоятельная геометрия не доказывает работу построителя. Внешнюю расстановку и ручные дополнения включать в проверку сборки.
