# Локальный MCP, Ruby и надежность операций

## 1. Выбор способа работы

При наличии зарегистрированного `sketchup-local` используй его. Начни с `sketchup_status`, затем читай нужный уровень `sketchup_objects` по parent_id с пагинацией. Не выгружай сырую геометрию всей модели, если нужен один шкаф.

Если инструменты еще не появились в текущем runtime, проверь актуальные README и клиент проекта. В текущем workspace fallback — `bridge/sketchup_api.py`: CLI поддерживает `info` и `ruby --file`; Python-функция `call` также принимает method/params. Не выдумывай CLI-команду `batch` или `layout_build`, если она не поддерживается парсером.

Не устанавливай дополнительный сервер/расширение только ради повторения уже доступного доступа. CUA используй для видимых функций, которых нет в MCP/API, при доступности и по правилам соответствующего инструмента.

## 2. Контракт текущего моста

Сверено с `bridge/mcp_server.py` в workspace 2026-09-30; при дальнейшем использовании перечитай схему при изменениях.

| Инструмент | Назначение и условия |
|---|---|
| sketchup_status | Связь, версия и активная модель; SketchUp открыт |
| sketchup_objects | Группы/компоненты, persistent IDs и границы mm; offset≥0, limit 1–100 |
| sketchup_batch | 1–100 действий, одна Undo-операция; box/room/cabinet/move/material/erase |
| sketchup_ruby | Ruby до 100000 UTF-8 bytes; один внешний Undo; компактный JSON-результат |
| sketchup_view | PNG текущего вида; ширина 320–2400, высота 240–2400 |
| layout_status | Возможность LayOut и шаблоны; опциональная сводка сохраненного .layout |
| layout_build | Сохраненный SKP → новый .layout и PDF, 1–20 листов |

Наличие функции в исходнике сервера не означает, что она уже доступна в tool catalog текущего чата. Проверяй реальные tools; не называй неисполненный запрос успешным.

`box`, `room`, `cabinet`: name, size_mm=[W,D,H], origin_mm, thickness_mm для последних двух, shelves для cabinet. `move` задает относительное смещение через origin_mm. `material` задает только цвет #RRGGBB, не PBR/текстуру. `erase` удаляет по ID. Для существующего объекта нужен persistent ID, а не позиция в списке.

`room` — стены и пол одной заданной толщины, без крыши; наружный W/D/H. При t внутренний свет W−2t, D−2t, высота над верхом пола H−t. Для другого пола или сложного плана требуется отдельная конструкция, обычно Ruby.

`cabinet` — упрощенная схема корпуса и равномерных полок, задник той же заданной толщины. Фасады, кромки, цоколь, техника, фурнитура, зазоры и карты присадки не появляются автоматически.

## 3. Примеры аргументов

Это проверенные по схеме примеры, не поручение добавить объекты в текущую модель.

```json
{"actions":[{"op":"room","name":"Учебная оболочка","size_mm":[4400,3400,3000],"thickness_mm":200,"origin_mm":[0,0,0]}],"label":"Создать учебную оболочку"}
```

Ожидаемый идеальный внутренний свет 4000×3000 mm, высота над верхом пола 2800 mm. Толщина пола 200 mm является учебным условием, не стандартом.

```json
{"actions":[{"op":"cabinet","name":"Учебный корпус","size_mm":[600,550,800],"thickness_mm":18,"shelves":2,"origin_mm":[1000,1000,200]}],"label":"Создать учебный корпус"}
```

18 mm — явный учебный параметр. Перед производственным применением материал и конструкцию выбирают по проекту. Не переносись с этой команды к утверждению, что шкаф готов.

## 4. Единицы Ruby и преобразования

SketchUp Ruby API хранит длины в inches независимо от единиц отображения. Для построений в mm используй Length через `.mm`, для выдачи — `.to_mm`. Не смешивай голое число координаты Ruby с mm в JSON моста. Для машинной сериализации используй числовое значение с явно указанной единицей; форматированный `Length#to_s` может округлять и использовать локальный десятичный разделитель.

Различай model.entities, active_entities и entities definition. Для целевой детали выбирай контекст явно; открытый пользователем режим редактирования не должен случайно определять место нового объекта.

Для вложенного объекта преобразование в мировую систему — композиция transformations родителей и экземпляра. Порядок умножения важен. Проверяй локальные оси, масштаб, отражение и единицы. После неравномерного масштабирования толщина/объем экземпляра могут отличаться от definition.

У SketchUp BoundingBox методы width/height/depth соответствуют X/Y/Z как ширина по X, extent по Y, extent по Z, а не бытовому W/H/D. Для ясной выдачи вычисляй разность max/min отдельно по x/y/z. Мировые габариты не подходят для раскроя повернутых деталей.

## 5. Транзакции и внешние эффекты

Мост уже оборачивает Ruby и batch в именованную операцию. Внутри `sketchup_ruby` не вызывай start_operation, commit_operation и abort_operation. В другом, самостоятельном расширении схему операции выбирай по официальному API; не копируй оболочку операции в код моста.

Собирай нужные изменения в один связанный пакет, но не объединяй независимые задачи ради максимального числа действий. До опасной правки сверяй ID/объект, после — фактические размеры и состав. Работай с target entities, не удаляй все entities модели.

Внешние записи, сеть, установки и процессы Undo не откатывает. Идентификатор и имя новых объектов должны помогать определить, состоялась ли запись после таймаута. Ruby-ответ ограничен мостом; возвращай компактные ID/размеры/счетчики, не огромные массивы геометрии.

## 6. Параметрические алгоритмы

Сохраняй повторяемый Ruby локально в проекте по принятой структуре. Отделяй входные параметры и проверку от генерации. Проверяй положительные размеры, толщины, внутренний свет, интервалы, число полок, координаты и ограничения выбранного механизма до создания geometry.

Стабильные IDs/атрибуты используй для обновления; не добавляй новый шкаф поверх старого при каждом запуске. Определи, что можно заменить и что принадлежит пользователю. Для общей definition либо меняй все предусмотренные экземпляры, либо осознанно отделяй нужный.

При добавлении нового алгоритма проверь граничные значения и неверные входы, rollback, размеры и сохранность посторонних объектов на разрешенном тестовом объекте/копии. Не используй активный клиентский проект как неоговоренный стенд.

## 7. Диагностика связи

После таймаута прочитай статус, нужные ID и выходные файлы. Таймаут клиента не доказывает отмену операции. Определи: приложение не отвечает, очередь не обрабатывается, запрос отклонен, результат слишком большой, файл уже создан или runtime не обновил инструменты.

Не повторяй подряд изменяющие вызовы и не нажимай случайные UI-элементы. Сохраняй компактный журнал: метод, время, label, ID и результат; без секретов и лишних данных. Перезапуск требует сохранности несохраненной работы и не заменяет диагностику причины.
