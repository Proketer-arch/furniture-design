# QA, документация и диагностика

## 1. Матрица приемки

| Стадия | Требуемая проверка | Доказательство |
|---|---|---|
| Исходные данные | Обмер, версия, материалы, нагрузки, ограничения | Источники и паспорт среды |
| Модель | Размерные цепи, типы деталей, контуры, структура | Численные значения/виды/native readback |
| Фурнитура/обработка | Артикулы, комплект, базы, стороны, глубины | Документы, таблицы, ответные детали |
| Документы | Виды, размеры, количества, IDs, редакция | Открытый экспорт/листы |
| Раскрой | Заготовки, количество, текстура, листы/остатки | Карты и сверка деталей |
| ЧПУ | Станок/профиль, инструменты, операции, переворот | Файлы, карта установки, симуляция/измерение по стадии |
| Смета | База, ресурс, операции, цены, методика | Расчет/источники/открытые позиции |
| Бирки/пакеты | Маркировка, состав и очередность | Сверка ID, печать/комплектование при выполнении |
| Обмен/облако | Редакция, права, ID, полнота данных | Readback и проверка требуемой стороны |

Не все стадии обязательны для каждой задачи. При локальной правке проверяй затронутые зависимости; успешные проверки без нового изменения/сомнения повторять не нужно.

## 2. Конструкторский комплект

Карточка: проект, изделие, редакция, единицы, версии программы/баз, источники размеров, статус, материальные/монтажные ограничения.

Деталировка:

`part_id | module_id | type | name | qty | finished_size | core/blank_size | units/axes | material_id | thickness | grain/face | edges | processing | drawing | revision`

Для каждой кромки укажи элемент контура/сторону, материал, толщину, подрезку/припуск и источник правил. «Кромка по кругу» недостаточна при разных сторонах и текстуре.

Обработка:

`operation_id | part_id | local_datum | side/face/edge | coordinates | diameter/width | depth | through/blind | direction | tool/process | tolerance | hardware_source | revision`

Это нейтральная структура контроля, не заявление о native-формате экспорта БАЗИС. Реальные поля/форматы проверь по документации выбранного модуля.

## 3. Чертежи и спецификации

Сборочный лист: габариты, базы, отметки, позиции, узлы, фасады, опоры и крепление. Детальный: пласть, текстура, толщины, кромки, обработки, базы, размеры и допуски. Монтажный: привязки к объекту, зазоры, основание, доступ, регулировка и очередность.

Автоматическое создание листов не гарантирует, что каждый содержит нужную информацию. Открой все требуемые листы, проверь отсутствие обрезки, правильную ориентацию, единицы, порядок размеров, редакцию и фактическую читаемость.

Спецификация должна различать материал, покупное изделие, механизм, крепеж, деталь комплекта и упаковку. Число экземпляров и definition/тип — разные базы учета. Не удваивай крепеж из модели и состава комплекта.

Для документов по ЕСКД/иному стандарту сначала установи требуемый стандарт и его актуальные правила. Наличие штатного шаблона не подтверждает соответствие конкретному нормативному выпуску или согласование.

## 4. Change impact

При смене ширины/высоты/толщины/материала/задника/кромки/механизма/базы/постпроцессора составь список зависимых объектов и артефактов. Пересчитай цепи, обнови обработку и документы, сверяй изменения.

Не сохраняй разные модели под одним revision. Производственные файлы старой редакции не удаляй молча: обозначь их статус и используемый выпуск по правилам проекта. Если предыдущие файлы уже переданы, требуется конкретная процедура замены в разрешенном объеме.

## 5. Диагностика без угадывания

Симптом → объект/версия → воспроизводимые условия → различающие гипотезы → узкая проверка → фактический результат → исправление → затронутая регрессия.

| Симптом | Проверять прежде исправления |
|---|---|
| Деталь другого размера | Чистовой/основа/заготовка, кромка/подрезка/припуск, единицы и экспорт |
| Отверстие на неверной стороне | ЛСК, пласть/торец, Owner/поворот, переворот и профиль станка |
| Фурнитура не попала в смету | Тип объекта, включение в учет, комплект, база, сопоставление артикула |
| После параметризации потеряна присадка | Тип элемента, правила обновления, растяжение, зависимый механизм |
| Скрипт работает не везде | Build/API, host, подключаемые модули, права, версия библиотеки |
| Раскрой не совпадает с моделью | Редакция, фильтры деталей, группирование, заготовка и количества |
| УП не принимается | Контроллер/постпроцессор, версия/кодировка/формат, инструменты и лицензионный режим |
| Неверная сумма | Единицы, даты цен, упаковки, двойной счет, метод маржи/наценки |
| Облачный результат не виден | Tenant/роль, тариф/услуга, версия источника, ID, статус задания, ссылка |
| Таймаут импорта/генерации | Реальный результат, созданные IDs/файлы/заказы, partial state |

Не исправляй неизвестный сбой обновлением всего комплекса или изменением базы наугад. Сначала проверь минимальный воспроизводимый пример. Форум может дать гипотезу, но параметры/контракт подтверждай первичными источниками.

## 6. Протокол тестового изделия

`fixture_id | input_revision | environment | library_version | parameters | expected_parts | expected_operations | expected_docs | actual | deviations | status`

Для сквозной проверки выбери небольшое изделие с асимметрией, разными кромками, глухой/сквозной обработкой, хотя бы одним механизмом и понятным количеством. Исполнимую УП создавай только при подтвержденной машинной среде. Не используй реальный клиентский файл как стенд без разрешенной копии.

Проверь: исходная модель → размеры/операции → документация → раскрой → ЧПУ/маркировка → смета/пакет → нужный обмен. Выполняй только необходимые стадии. В фикстуре должны быть заранее определенные ожидаемые результаты, а не сравнение программы с самой собой.

## 7. Уровни подтверждения

- Анализ официальной функции: возможность найдена в документе.
- Подготовка: файл/код/ТЗ созданы.
- Статическая проверка: структура/логика проверены вне host.
- Проверка в БАЗИС: выполнено в конкретном build с readback.
- Проверка обмена/облака: результат прочитан на принимающей стороне.
- Проверка ЧПУ: выполнен указанный уровень симуляции/контроля.
- Первое изделие: измерено/собрано с протоколом.
- Разрешенный выпуск: имеется решение ответственного для конкретной редакции.

Один уровень не доказывает следующий. Если этап не выполнен, так и напиши; не заменяй его уверенной формулировкой.

## 8. Реестр замечаний

`issue_id | part/module/file | evidence | consequence | priority | correction | owner | status | verification`

Блокер выпуска — ошибка/неизвестное, мешающее конкретной следующей стадии. Декоративное пожелание не должно скрывать производственный блокер. Закрывай замечание после фактической проверки исправленного результата.

## 9. Краткая выдача

Начинай с результата. Передай файлы/редакции, состав, что изменено, как проверено, что остается открытым и что должен сделать ответственный. Отдельно укажи несовместимость версии/оборудования, неизвестные коммерческие данные и границы доступа.

Для простой задачи ответ короткий. Для сложного выпуска используй таблицу артефактов и проверок; не пересказывай всю историю инструментов.
